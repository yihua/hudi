# RFC-117: Snapshot Manifest

## Proposers

- @yihua

## Approvers

- TBD

## Status

Issue: [#20464](https://github.com/apache/hudi/issues/20464)

> Please keep the status updated in `rfc/README.md`.

## Abstract

To plan a snapshot read, a query engine needs the snapshot, the partitions, the file slices in each
partition, and per-file statistics. Today Hudi answers that with a chain of dependent object storage
calls: timeline listing, per-instant metadata reads, then the metadata table (MDT), which is itself a
merge-on-read table with its own timeline, base files, and log files. The chain is the same length for a
table with twenty files as for one with a million, so Hudi reads do not scale down.

This RFC adds an optional, immutable, engine-neutral **snapshot manifest**: one Parquet file under
`.hoodie/snapshot/` holding every live file slice and its statistics for one snapshot. A reader that
finds a manifest and proves it current, using the timeline listing it issues anyway, plans after two
dependent round trips and four requests regardless of partition count, file count, timeline length, or
MDT state. An atomically replaced **latest pointer** lets a reader that trusts the table's writers skip
the timeline listing as well: two requests in one round trip when the manifest is embedded in the
pointer. A reader that finds no manifest, or a stale one, takes the existing path. The commit protocol, the timeline, the
MDT, and `hoodie.properties` do not change, and the manifest works on table versions 6 through 9.

## Background

### What a reader does today, in filesystem calls

The table lists every object storage call `hudi-common` makes for a snapshot query, with the MDT off
and on. hudi-rs implements the same protocol with the same call shape, so DataFusion and DuckDB pay the same. Call
types: **LIST** (one request per page of up to 1,000 entries), **GET** (whole object), **RANGE**
(byte-range read), **HEAD** (existence check). Symbols: P partitions, D partition directory depth, F
files, T active timeline instants, R completed replace commits, K pending compaction, log compaction,
and clustering plans, L log files in the MDT's latest `files` slice (up to
`hoodie.metadata.compact.max.delta.commits`, default 10), C predicate columns, G `column_stats` file
groups.

| Step | Code | Without MDT | With MDT |
|---|---|---|---|
| Table config | `HoodieTableConfig`, `ConfigUtils.fetchConfigs` | 1 GET `hoodie.properties` | same |
| Active timeline | `HoodieTableMetaClient.scanHoodieInstantsFromFileSystem` | 1 LIST of `.hoodie/` (v6) or `.hoodie/timeline/` (v8+), more pages as T grows | same |
| Schema | `TableSchemaResolver.getLatestCommitMetadataWithValidSchema` | 1 GET of commit metadata, more when recent instants carry no schema | same |
| Replaced file groups | `AbstractTableFileSystemView.resetFileGroupsReplaced` | R GETs, one per completed replace or clustering commit in the active timeline | same |
| Pending plans | `AbstractTableFileSystemView.init`, `CompactionUtils`, `ClusteringUtils` | K GETs | same |
| Completion times of old log instants (MOR, v8+) | `CompletionTimeQueryViewV2.loadCompletionTimeIncrementally` | 2 GETs (`history/_version_`, manifest) plus 1 RANGE per archived Parquet file in range, when a log file's instant is archived | same |
| MDT open | `HoodieBackedTableMetadata.initIfNeeded` | none | 1 GET `metadata/.hoodie/hoodie.properties`, 1 LIST of the MDT timeline |
| MDT `files` slice | `HoodieTableMetadataUtil.getFileSystemViewForMetadataTable` | none | 1 LIST of `metadata/files/`, 1 GET per pending MDT compaction plan |
| Valid instants | `HoodieTableMetadataUtil.getValidInstantTimestamps` | none | 1 GET per completed rollback or restore newer than the last MDT compaction |
| Partition discovery | `FileSystemBackedTableMetadata.getPartitionPathWithPathPrefixes` | 1 LIST per directory above the leaves, 1 HEAD per subdirectory for `.hoodie_partition_metadata`; D dependent levels | 3 RANGEs to open the `files` HFile (trailer, load-on-open section, data block of `__all_partitions__`), then L log files each opened and scanned |
| File listing | `HoodieTableMetadata.getAllFilesInPartitions` | P LISTs, one per partition | 1 RANGE per data block holding the P partition keys; readers reused within one `HoodieBackedTableMetadata` instance |
| Column statistics | `ColumnStatsIndexSupport`, `HoodieBackedTableMetadata.getRecordsByKeyPrefixes` | none at planning time on Spark; 2 RANGEs per file for Parquet footers on hudi-rs (2F) | after the listing, for each of G file groups: 3 RANGEs to open the HFile, up to C RANGEs for prefix data blocks, L log files opened and scanned; readers not reused for this partition |
| Partition statistics | `PartitionStatsIndexSupport` | none | same shape on `partition_stats` |
| **Calls** | | 5 + R + K + directories + P HEADs + P LISTs | 9 + R + K + 2L + G × (3 + C + L), plus 1 per recent rollback |
| **Dependent round trips** | | at least 4 + 2D | at least 9 + L for the listing, then 3 + L for statistics |

Statistics lookups are keyed by file name, so they cannot start before the listing completes. Every
other step depends on the one above it.

### Why this does not scale down

- **The cost is fixed, not proportional.** With the MDT on, at least 9 + L dependent round trips and
  9 + R + K + 2L calls precede the first partition's file list, regardless of file count. Each round
  trip is a full object store latency.
- **The active timeline multiplies it.** Replaced file groups, pending plans, and recent rollbacks cost
  one GET each. Clustering every ten commits under the default archival window
  (`hoodie.keep.min.commits` 20, `hoodie.keep.max.commits` 30) gives R = 2 to 3 replace-commit GETs per
  query, and R grows without bound when archival lags. None of them carry information that changed
  since the reader's last query.
- **The MDT costs more than the data it describes.** For a small table, `files` and `column_stats` are
  each an HFile plus up to ten log files, behind the MDT's own properties, timeline, and compaction
  state. Consuming them needs an HFile reader, a log block reader, the key hashing scheme (base64 of
  64-bit and 128-bit hashes of column, partition, and file name), and the valid-instant filter across
  two timelines. Every non-JVM engine reimplements all of it before it can list a ten-file table.
- **Without the MDT, partitions mean calls.** One LIST per directory level, one HEAD per subdirectory,
  one LIST per partition, footer reads per file for statistics; latency grows with D and P.
- **Statistics are a second pass**, per column, after the listing, over every `column_stats` file
  group and its log files.
- **A cached view has no cheap currency check.** Engines either rebuild per query or serve stale
  results behind a TTL.

The manifest is not a new commit protocol and does not replace the timeline or the MDT. Record index,
bloom filters, secondary and expression indexes stay in the MDT. The manifest is derived data: it can
be deleted at any time, is rebuilt from the timeline and the file system view, and is never trusted
without a check against the timeline.

## Goals and non-goals

Goals:

1. A snapshot read resolves partitions, file slices, and per-file statistics in two dependent round
   trips and four requests, independent of P, T, R, L, C, and G; one round trip and two requests with
   a trusted, inlined pointer.
2. Optional. No table configuration; a table with manifests is otherwise byte-identical, and every
   existing reader, including 0.14 and 0.15 readers on v6 tables, ignores the manifest directory.
3. Correct whenever used. By default a reader uses a manifest only after proving, from the timeline
   listing it issues anyway, that no instant has completed since the manifest was built. A reader that
   opts to trust the pointer gets a consistent snapshot with a stated staleness bound.
4. Table versions 6 to 9, copy-on-write and merge-on-read, with or without the MDT.
5. Engine-neutral: LIST, GET, and a Parquet reader are enough. One Java implementation serves Spark,
   Trino, Flink, and Hive; one Rust implementation serves DataFusion, DuckDB, and the Python bindings.

Non-goals (see Future work): tables above the manifest size cap, time travel and incremental queries
through manifests, point lookups and record-level indexes, any change to the write path's use of the
file system view or the MDT.

## Design

### What every engine needs

Planning looks the same in a Spark driver, a Trino coordinator, or a single DataFusion or DuckDB
process: resolve the snapshot, prune partitions, enumerate file slices (base plus ordered logs for
snapshot reads, base only for read-optimized), prune files on per-file statistics and feed row and byte
counts to the cost model, then cache the result and know cheaply whether it is still current.

The manifest maps each step to one in-memory operation over one parsed file. Statistics are typed, one
row per file slice, so an engine hands each row to its own file statistics type (Spark's data skipping
expressions, DataFusion's per-file `Statistics`, DuckDB's bind-time pushdown, Trino's `TupleDomain`)
without Hudi's key-value index model. The manifest's name is unique and its content immutable, so an
engine caches the parsed object by name and re-validates with one LIST.

### Layout

```
<base>/.hoodie/
  hoodie.properties                       unchanged
  timeline/ (v8+) or . (v6, v7)           unchanged
  metadata/                               unchanged
  snapshot/                               new
    <snapshotInstant>_<buildTime>_<token>.manifest.parquet
    latest                                  pointer to the newest manifest
```

- `snapshotInstant`: the largest requested time among the completed instants the manifest covers.
  `buildTime`: the writer's clock in instant format. `token`: a short random suffix. Names sort by
  snapshot first and never collide across writers.
- Created with create-if-absent semantics (`HoodieStorage.createImmutableFileInPath`: direct create on
  S3, GCS, ABFS; temp file plus rename on HDFS and local). Never modified afterwards.
- `latest` names the newest manifest and is replaced atomically on each publish (see Latest
  pointer). A reader that does not trust it, or finds it missing, lists `.hoodie/snapshot/`, which holds
  at most `hoodie.snapshot.manifest.retained` manifests (default 3).

### File format

One Parquet file, Zstd compressed, one row per live file slice.

| Column | Type | Notes |
|---|---|---|
| `partition_path` | string | Relative partition path; empty for non-partitioned tables |
| `file_id` | string | File group id |
| `base_instant` | string | Requested time of the slice's base instant |
| `base_file` | struct { `name` string, `size` long, `record_count` long } | Null for log-only slices on MOR |
| `log_files` | list of struct { `name` string, `size` long } | In apply order; empty on COW |
| `stats` | struct { `<column>`: struct { `min` T, `max` T, `null_count` long, `value_count` long, `tight` boolean } } | Null when statistics are not collected; `T` is the column's Parquet type |

- The row holds the slice a snapshot reader must read. For a file group with a pending compaction that
  is the merged slice, previous base plus all logs on both sides of the compaction instant, as
  `AbstractTableFileSystemView.getLatestMergedFileSlicesBeforeOrOn` returns today. Replaced file groups
  are absent. Readers need no pending plans and no replace metadata.
- `stats` is a struct of structs rather than one row per (file, column), so a planner reads one row per
  file and Parquet projection fetches only the predicate columns. Nested columns use their dotted path
  as the field name. A slice with log files carries the union of its files' ranges with `tight = false`.
- The statistics column set is the one the column statistics index would index
  (`hoodie.metadata.index.column.stats.column.list`, else all top-level columns up to the cap).

Footer key-value metadata:

| Key | Content |
|---|---|
| `hudi.snapshot.format.version` | `1`; additive columns and keys do not bump it, a higher major version makes readers fall back |
| `hudi.table.version` | Table version at build time |
| `hudi.snapshot.instant` | Same as the file name's `snapshotInstant` |
| `hudi.snapshot.completed.instants` | Sorted requested times of every completed instant in the active timeline at build time |
| `hudi.snapshot.pending.instants` | Requested or inflight instants at build time (informational) |
| `hudi.snapshot.file.slices` | Row count |
| `hudi.snapshot.stats.columns` | Statistics column names, or empty |
| `hudi.table.schema` | Avro schema of the latest commit metadata, so readers skip the schema GET |
| `hudi.snapshot.writer` | Hudi version and engine |

### Validity rule

Let `M` be `hudi.snapshot.completed.instants` and `L` be the requested times of the completed instants
in the reader's current listing of the active timeline (completed state extension on v6, completion time
in the name on v8+; `history/` and `.crc` entries ignored).

**A manifest is valid for the latest snapshot if and only if `L ⊆ M`.**

- Any instant completed after the build is in `L` and not in `M`, whatever its requested time: a
  concurrent writer's commit, a compaction or clustering requested before the build and completed
  after, a clean, a rollback of a completed instant (itself a completed instant), a restore, a
  savepoint, an indexing commit.
- Archival only removes from `L`, which keeps the relation. Rolling back a pending instant adds a
  completed rollback instant, which invalidates.
- Because every completed instant invalidates, a valid manifest never references a cleaned file and
  never misses an added one. Correctness does not depend on who built the manifest or with what
  version: an older writer or another engine leaves a stale manifest, which the check rejects.

Readers try the newest manifest by name, then the next (concurrent writers can publish out of order),
then fall back. Fallback is never an error.

### Read path

```
RT1 (parallel):  GET .hoodie/hoodie.properties      LIST .hoodie/snapshot/
RT2 (parallel):  LIST <timeline dir>                GET <newest manifest>
in memory:       check L ⊆ M; parse rows; serve partitions, slices, stats, schema
```

Two dependent round trips, four requests. The properties read comes first because the timeline
directory depends on the table version. An empty `.hoodie/snapshot/` costs one LIST issued in parallel
with a request made anyway. Readers cache parsed manifests by name; a repeat query at the same snapshot
is two parallel LISTs and a cache hit. With the pointer, the snapshot LIST in RT1 becomes a GET of
`latest`, and a reader that trusts the pointer drops the timeline LIST from RT2:

```
RT1 (parallel):  GET .hoodie/hoodie.properties      GET .hoodie/snapshot/latest
RT2:             GET <manifest named by the pointer>   (skipped when the pointer embeds it)
```

| Mode | Requests | Dependent round trips |
|---|---|---|
| Manifest, listing check (default) | 4: 2 GETs, 2 LISTs | 2 |
| Pointer for discovery, listing check | 4: 3 GETs, 1 LIST | 2 |
| Trusted pointer | 3 GETs | 2 |
| Trusted pointer, manifest inline | 2 GETs | 1 |
| Repeat query, manifest cached | 2 LISTs, or 1 GET of the pointer | 1 |

### Latest pointer

`.hoodie/snapshot/latest` is a small JSON object:

```json
{"version": 1, "manifest": "20261028021500000_20261028021501200_a1b2.manifest.parquet",
 "snapshotInstant": "20261028021500000", "buildTime": "20261028021501200",
 "completedInstants": ["...", "..."], "inline": null}
```

- **Atomic replacement.** Each publish writes the whole object: a single PUT on S3, GCS, and ABFS,
  which are atomic and strongly consistent per object, and temp file plus rename on HDFS and local
  (`HoodieStorage.createImmutableFileInPath` with a temp file, then `rename`). A reader sees the old
  pointer or the new one, never a partial write.
- **Monotonic.** The pointer carries `snapshotInstant` and `buildTime`. When a write lock is configured
  the pointer is updated inside it, so updates are serialized. Without a lock two writers can race and
  the last PUT wins; a reader ignores any pointer whose (`snapshotInstant`, `buildTime`) is below the
  one it last used, so a regression is a transient fallback, never a wrong read.
- **Inline manifest.** When the manifest is under `hoodie.snapshot.manifest.pointer.inline.max.bytes`
  (default 256 KB, a few hundred slices with statistics), the pointer embeds it base64-encoded and the
  reader needs no second GET.

Two ways to use it:

1. **Discovery only** (default). The pointer replaces the LIST of `.hoodie/snapshot/`; the timeline LIST
   and the `L ⊆ M` check still run, with `M` taken from the pointer's `completedInstants`. Same
   correctness as before, one GET instead of one LIST.
2. **Trusted** (`hoodie.snapshot.manifest.pointer.trust=true` on the reader). The timeline LIST is
   skipped. The reader serves the snapshot the pointer names. This is correct only if every writer of
   the table publishes manifests, because a non-publishing writer's commit leaves the pointer behind
   and nothing in this mode can detect it. The guarantee in this mode is therefore: a consistent
   snapshot no older than the last publish, bounded by `hoodie.snapshot.manifest.pointer.max.staleness`
   (default 1 hour): a reader that finds `buildTime` older than the bound falls back to the listing
   path. A stale pointer can only serve an older committed snapshot; it cannot mix states. If a data
   file named by a stale manifest has since been cleaned, the read fails on open, and the reader
   refreshes through the listing path and retries. Enabling trust is a deployment decision, taken when
   the writers are known, not a table property.

The default stays discovery only, because the listing path is what makes the manifest safe against
writers that do not know about it.

### Write path

One hook, `SnapshotManifestWriter.publish(HoodieTable)`, runs after the write client completes any
action (commit, delta commit, replace commit, compaction, log compaction, clean, rollback, restore,
savepoint, indexing), after `TransactionManager.endStateChange` and outside the lock. It is best
effort: a failure is logged and the commit stands. Flink and the Java client reach it through the same
`BaseHoodieWriteClient` and `BaseHoodieTableServiceClient` paths as Spark.

1. Reload the active timeline; compute `M` and the pending set.
2. Build a file system view on that same timeline over the table's `HoodieTableMetadata` (MDT when
   enabled, else storage listing) and take the latest merged file slices per partition. `M` and the
   rows must come from one timeline load, or a completion between the two would be in `M` and not in
   the rows.
3. Attach statistics. Files written by the completing action reuse the `HoodieColumnRangeMetadata`
   computed for the column statistics index update (base files via
   `HoodieTableMetadataUtil.readColumnRangeMetadataFrom`, log files via `HoodieWriteStat.recordsStats`).
   Unchanged slices carry their row over from the previous manifest. With no previous manifest, read
   `column_stats` once. Statistics are present if and only if the column statistics index is enabled.
4. Write with create-if-absent semantics.
5. Replace `latest` atomically, inside the write lock when one is configured.
6. Delete manifests beyond the retention count, oldest first, never the one `latest` names.

Publication is skipped above `hoodie.snapshot.manifest.max.file.slices` (default 10,000, which is
1.2 TB at 128 MB base files). Per action the writer pays one listing pass, one GET of the previous
manifest, and one PUT, never inside the critical section.

### Configuration

Write and read client configs only; nothing in `hoodie.properties`.

| Config | Default | Meaning |
|---|---|---|
| `hoodie.snapshot.manifest.enable` | `false` at first, then `true` | Publish after each completed action |
| `hoodie.snapshot.manifest.max.file.slices` | `10000` | Skip publication above this count |
| `hoodie.snapshot.manifest.retained` | `3` | Manifests kept under `.hoodie/snapshot/` |
| `hoodie.snapshot.manifest.read.enable` | `true` | Use a valid manifest when present; kill switch |
| `hoodie.snapshot.manifest.pointer.inline.max.bytes` | `262144` | Embed the manifest in `latest` below this size |
| `hoodie.snapshot.manifest.pointer.trust` | `false` | Skip the timeline LIST and serve the pointer's snapshot |
| `hoodie.snapshot.manifest.pointer.max.staleness` | `1h` | In trusted mode, fall back to the listing path for an older pointer |

Defaults: the writer flag starts `false` so a release can ship the reader adapters and the validation
tool before any table carries a manifest. The cap of 10,000 slices bounds the manifest: a synthetic
manifest of 10,000 slices with statistics for 30 columns of random values measures 12.9 MB
uncompressed and 7.7 MB with Zstd, so one GET stays cheaper than the MDT path it replaces; tables
above the cap already have the MDT. The test plan repeats the measurement on real tables.

### Engine integration

Two implementations of one normative format, each doing resolve (pointer GET or snapshot LIST,
timeline LIST unless trusted, manifest GET, the subset check), parse, serve.

**Java.** `SnapshotManifestResolver` in `hudi-common` returns `Option<SnapshotManifest>`. Two adapters
plug into the seams every Java engine already uses:

- `SnapshotManifestTableMetadata implements HoodieTableMetadata`: `getAllPartitionPaths`,
  `getAllFilesInPartition(s)`, `getColumnStats`, and `getRecordsByKeyPrefixes` for `column_stats` and
  `partition_stats` are served from rows (partition statistics aggregated on the fly); record index,
  bloom filter, and secondary index calls delegate to a lazily created `HoodieBackedTableMetadata`.
  `HoodieTableMetadata.create` returns it when a valid manifest resolves.
- `SnapshotManifestFileSystemView implements SyncableFileSystemView`: `getPartitionPaths`,
  `getLatestFileSlices`, `getLatestMergedFileSlicesBeforeOrOn` at the snapshot instant,
  `getLatestBaseFiles` serve stored slices without `init()`'s per-instant reads; history and
  pending-operation queries delegate to a lazily built standard view. `FileSystemViewManager`
  selects it under the same condition.

`BaseHoodieTableFileIndex` (Spark and Flink), `ColumnStatsIndexSupport` and
`PartitionStatsIndexSupport`, the Flink `FileIndex`, Hive input formats, and the `hudi-trino` listers
and `HudiIndexSupport` strategies then use the manifest with no engine-specific code.
`TableSchemaResolver` consults `hudi.table.schema` before reading commit metadata.

**Rust.** `SnapshotManifest::resolve` in `hudi-rs` core beside the MDT path in
`Table::get_file_slices_inner`; `FileSystemView::load_file_groups` takes manifest rows as a third
source; `apply_stats_pruning` takes manifest statistics as Arrow arrays. DataFusion's `HudiDataSource`
and the DuckDB extension consume through `Table`, and the C ABI exposes per-slice statistics for
DuckDB's own pruning.

**Any other reader** needs LIST, GET, a Parquet reader, and the active timeline's file name grammar.

### Table versions and compatibility

- v6 and v7 list `.hoodie/` with `<time>.<action>[.requested|.inflight]`; v8 and v9 list
  `.hoodie/timeline/` with `<requested>_<completed>.<action>`. `TimelineLayout` and hudi-rs handle
  both; the rule only needs completed or not per name.
- Every existing timeline scan filters by a known extension set
  (`HoodieTableMetaClient.scanHoodieInstantsFromFileSystem` on 0.14, 0.15, 1.x; hudi-rs
  `TimelineLoader`), so `snapshot/` is ignored like `.aux`, `.temp`, `.schema`, `archived`, and
  `metadata`.
- The manifest is not part of the table version. Upgrade and downgrade ignore it; a stale manifest
  after either is rejected by the rule.

### Guarantees and failure modes

- **Correct when used**: served only after `L ⊆ M` holds against this query's listing. The only
  remaining risk is a writer bug storing a wrong slice set, which the validation tool and tests
  target, and `hoodie.snapshot.manifest.read.enable=false` disables use entirely.
- **Fast when present**: two dependent round trips and one bounded file; one round trip with a
  trusted, inlined pointer.
- **Invisible when absent**: one extra GET or LIST, in parallel with a request issued anyway.

| Event | Effect |
|---|---|
| Writer crashes after completing the instant, before publishing | No manifest for that state; fallback until the next action publishes |
| Manifest corrupt or unreadable | Fallback |
| Two writers publish out of order | Newest two names tried; at worst fallback for one commit cycle |
| Manifest deleted by retention between LIST and GET | 404; fallback |
| Writer without manifest support commits | Stale manifest rejected |
| Table exceeds the slice cap | Publication stops; stale manifest rejected; existing path serves |
| Pointer missing or unparseable | LIST of `.hoodie/snapshot/`, then the listing path |
| Pointer regresses after a lock-free race | Ignored by readers that saw a newer one; next publish repairs it |
| Trusted mode, non-publishing writer commits | Older consistent snapshot served until the staleness bound, then fallback; a cleaned file fails on open and forces a refresh |

## Implementation plan

Phase 1, Java, as a stack of PRs on `apache/hudi` master:

1. **Format and model** (`hudi-common`): `SnapshotManifest`, row model, Parquet writer and reader over
   `HoodieIOFactory`, footer metadata, statistics type mapping; round-trip and schema evolution tests.
2. **Resolver** (`hudi-common`): `SnapshotManifestResolver` with the validity rule; a test matrix over
   every action type on v6 and v8/v9 fixtures.
3. **Writer hook** (`hudi-client-common`): `SnapshotManifestWriter`, configs, cap and retention,
   statistics carry-over, the `publish` call site after each completed action; functional tests
   asserting rows equal the file system view's latest merged slices after every action.
4. **Reader adapters**: `SnapshotManifestTableMetadata`, `SnapshotManifestFileSystemView`, factory
   wiring, `TableSchemaResolver` shortcut; engine tests asserting identical results and pruned file sets
   with manifests on and off.
5. **Tooling**: `show_snapshot_manifest`, `validate_snapshot_manifest` (manifest versus file system
   view), `rebuild_snapshot_manifest` as Spark procedures and `hudi-cli` commands; metrics for publish
   latency, manifest size, hit versus fallback.

Phase 2, Rust (`hudi-rs`): resolver, parser, file system view source, statistics pruning, DataFusion
and DuckDB coverage against Java-produced fixtures; then a hudi-rs writer.

Phase 3: flip `hoodie.snapshot.manifest.enable` to `true` once a release has shipped the reader
adapters and the validation tooling.

## Rollout/Adoption Plan

- **Impact on existing users**: none. Writers do not publish unless enabled, readers never use an
  unvalidated manifest, and every existing reader ignores the directory.
- **Phasing out older behavior**: not applicable. The existing read path stays and is the fallback.
- **Migration tools**: none. The first publish after enabling builds a full manifest; disabling leaves
  at most `retained` small files, rejected once the table changes; deleting `.hoodie/snapshot/` is
  always safe.
- **Removal of existing behavior**: not proposed.

## Test Plan

The RFC is validated when:

- [ ] Format round trip passes for all Hudi column types, including decimal, timestamp, and nested.
- [ ] The validity rule passes a matrix over commit, delta commit, compaction (requested, inflight,
      completed), clustering, clean, rollback of pending and of completed, restore, savepoint,
      archival, and concurrent writers, on v6 and v8/v9 name grammars.
- [ ] After every action type, manifest rows equal the file system view's latest merged slices and
      manifest statistics equal the MDT's column statistics, on COW and MOR, partitioned and not, MDT on
      and off, multi-writer OCC on.
- [ ] Spark SQL, Flink, and Trino suites with manifests enabled return identical results and prune
      identical file sets to the runs with manifests disabled; hudi-rs reads Java-produced fixtures and
      returns the same slices and statistics.
- [ ] Object store calls and dependent round trips per query, counted with an instrumented
      `HoodieStorage`, are measured on tables of 10, 1K, 10K, and 100K files with active timelines of
      30, 300, and 3,000 instants, MDT on and off; manifest size and build latency set the default cap;
      planning latency on S3 is measured for Spark and for hudi-rs with DataFusion. No number is
      published before this.

## Future work

- **Time travel and incremental planning**: one manifest per completed instant within the active
  timeline; a query as of `T` uses the manifest whose snapshot instant is the latest completed instant
  at or before `T`, with the subset rule restricted to instants at or before `T`; the change set between
  two instants is the row difference of two manifests.
- **Larger tables**: a manifest list plus one manifest per partition, published asynchronously by a
  table service.
- **Mergeable distinct-count sketches** as an additive `stats` field.

## Alternatives considered

- **Pointer as the only discovery mechanism**, with no manifest listing fallback. A missing or
  corrupt pointer would then disable the fast path until the next publish; keeping the LIST fallback
  costs nothing.
- **Trusted pointer by default.** Rejected because it makes correctness depend on every writer of the
  table, which no table property can enforce on a writer that predates it.
- **Manifest embedded in commit metadata.** Bloats every instant file and saves no round trip; commit
  metadata is read after the timeline LIST either way.
- **Publishing inside the critical section**, named by the instant. Lengthens lock hold time, leaves
  orphans on crash, and still needs the subset rule because of out-of-order completion.
- **Trusting the manifest without the timeline check**, under a table property that obliges all
  writers. Breaks on the first commit from an older writer or another engine.
- **Avro or JSON.** No typed statistics with column projection, and DataFusion and DuckDB have native
  Parquet readers but no native Avro reader.
- **Reading the MDT's base HFiles directly.** Brings back the MDT timeline, the log files between
  compactions, the HFile reader, and the key hashing on every engine.

## Appendix A: worked example

A copy-on-write table on S3, version 8, one partition level, P = 12, F = 80, 45 active instants with
R = 3 clustering commits and K = 1 pending plan, column statistics index with G = 2 file groups, L = 5
log files since the last MDT compaction, a query with C = 3 predicate columns. Counts follow the
Background table and are derived from the code paths, not measured.

| | Without MDT | With MDT | Manifest, default | Manifest, trusted pointer |
|---|---|---|---|---|
| Table config and timeline | 1 GET, 1 LIST | 1 GET, 1 LIST | 2 GETs, 1 LIST | 2 GETs |
| Schema, replace commits, pending plans | 5 GETs | 5 GETs | none | none |
| MDT open and `files` slice | none | 2 GETs, 2 LISTs | none | none |
| Partition discovery and file listing | 1 LIST, 12 HEADs, 12 LISTs | 4 RANGEs, 5 log file scans | 1 GET | 1 GET, or none when inline |
| Column statistics | none on Spark; 160 RANGEs on hudi-rs | 2 × (3 + 3 + 5) = 22 RANGEs and scans | none | none |
| **Total calls** | 32 (192 on hudi-rs) | 42 | 4 | 3, or 2 when inline |
| **Dependent round trips** | 6 | 23 | 2 | 2, or 1 when inline |

A repeat query at the same snapshot with a manifest is two parallel LISTs and a cache hit.
